# コーディングスタイル（層 1: 表記）

可読性とレビュー容易性を保つための実装規約。
**`ruff`（lint / format）と `pyright`（型）で機械的に検証できる項目はツールに委ね、
ここには機械強制できない人手ルールだけを書く。**
どちらがどこに書かれているかは [README.md](./README.md) の「正本マップ」を参照する。

## 型ヒント

型ヒントの付与漏れ（`ANN`）とチェックの厳しさは機械強制されるため、ここには方針だけ書く。

- 前方参照はファイル先頭の `from __future__ import annotations` で解決し、
  戻り値型を文字列リテラルで書かない。
- 任意型が必要な場合は `typing.Any` を使う。ただし引数を `Any` で受けるのは
  契約を放棄することなので原則禁止し、許容するなら**外部由来の生値を受け取る境界に限る**。

> 例（このプロジェクトでの適用）
>
> YAML の生値を扱う `config.schema` の factory だけ `create(raw: Any)` を許容している
> （`ruff.toml` の `per-file-ignores` で `ANN401` を緩和）。

## 命名

| 対象 | 規則 | 例 |
|---|---|---|
| モジュール | `lower_with_under` | `data_loader.py` |
| クラス | `CapWords` | `ModelEvaluator` |
| 関数・メソッド・ローカル変数 | `lower_with_under` | `calculate_area` |
| 定数 | `CAPS_WITH_UNDER` | `MAX_ITERATION` |
| private 属性 | 先頭アンダースコア 1 つ | `self._config` |

大文字小文字の形式そのものは `ruff` の `N`（pep8-naming）が機械強制する。
以下は機械では判定できない、**名前の意味**に関する取り決め。

- メソッドの第 1 引数は `self`、クラスメソッドは `cls`。
- bool は判断内容が分かる名前に（`is_xxx` / `has_xxx` / `can_xxx` / `should_xxx`）。
- 名前は「処理・役割と一致」させる。`calculate_xxx()` が計算ついでに保存までしない、など。
- 過度な省略（`gen_pred_ms`）も、抽象的すぎる名前（`info`）も避ける。
- 日本語のローマ字読みは避ける（英語化が困難な固有名詞・ドメイン用語を除く）。
- 役割が定型のモジュールは、役割が名前から分かる接頭辞を付ける。

> 例（このプロジェクトでの適用）
>
> ファクトリーのモジュールは `factory_` で始める（`factory_model_builder.py`）。
> 設定・カタログの YAML はインデントを半角スペース 2 とする
> （Python 側は `ruff.toml` の `indent-width` に従う）。

## 禁止事項

機械強制されるものも一覧に残す。レビュー時に「なぜこれが CI を通っているのか」を
判断できるよう、**強制手段**を併記する。「人手」の行だけがレビューで見るべき対象。

| 禁止事項 | 強制手段 |
|---|---|
| スター import（`from x import *`） | `ruff` F403 |
| `global` 文によるグローバル変数の更新 | `ruff` PLW0603 |
| 素の `except:` | `ruff` E722 |
| `print`（代わりにロガーを使う。テストコードも対象） | `ruff` T201 |
| `except BaseException:` | 人手 |
| 1 文字変数（例外: ループの `i` / `k` / `v`、`except` の `e`、`with` の `f`） | 人手 |
| 予約語・組み込み関数と同名の変数 | 人手 |
| 本番コードの `assert`（テストコードは可） | 人手 |
| クラスの private 属性への外部からの直接アクセス | 人手 |

## モジュールサイズの目安

長すぎるモジュールは可読性を下げるため、分割を**検討する目安**を置く。
機械強制はしない（行数・複雑度を見る lint ルールは採用していない）。
厳格な上限ではなく、超える場合は「なぜ超えているか」を残す運用とする。

- 関数: 40 行程度（Google Style 由来）
- クラス: 300 行程度
- ファイル: 500 行程度
- 分岐・文の数: 過度に増えたら分割を検討する

目安を超えるとき、無理に割らず**意図を残す**:

- パッケージ／ファイル単位の事情は、`__init__.py` や代表モジュールの docstring に
  「分割方針・まとめている理由」を書く（既存コードでも `分割方針:` を記載している）。
- 単一の関数・クラスがやむを得ず長い場合は、docstring か `# NOTE:` に理由を書く。

点検は目視、または `lizard` 等での随時計測にとどめる。

## docstring・コメント

docstring の書式は機械強制されていない（理由は `ruff.toml` の `[lint.pydocstyle]` 参照）。
以下はすべて人手で守る。

- クラス・関数・メソッドには原則 **Google スタイル**の docstring を付ける
  （「private かつ短く自明」なものは省略可）。
- docstring には**呼び出し側が中身を読まずに使える情報**を書く（目的・引数・戻り値・送出例外）。
  実装の詳細はコード内コメントで説明する。
- narration コメント（コードをそのまま言い換えるだけのコメント）は付けない。
  コメントは**コードから読み取れない意図・制約・トレードオフ**を書く。
- 注意喚起は `# NOTE:` / `# TODO:` / `# FIXME:` / `# HACK:` / `# WARNING:` / `# OPTIMIZE:` を用いる。

## 設計ドキュメントの数式

Markdown の数式は `$...$`（インライン）／`$$...$$`（ブロック）で書く。
`\(...\)` / `\[...\]` はレンダリング差異が出やすいため使わない。

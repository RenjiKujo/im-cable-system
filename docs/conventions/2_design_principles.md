# 設計原則: インターフェース駆動と生成の分離（層 2: 設計原則）

クラスを実装するときに守る中核方針。狙いは **「実装を差し替え可能にし、依存を一方向に保ち、
生成箇所を一点に集約する」** こと。同じ役割で中身だけ違う実装が増え続けるコードベースで効く。

## 1. 実装ではなく抽象に依存する（Program to an interface）

具体的な処理を持つクラス（実装クラス）は、必ず対応する**インターフェース**（抽象基底クラス）を実装する。
利用側はインターフェース型だけを知り、どの具象が来るかは知らない。

- 公開メソッドはすべてインターフェースに宣言する。実装固有の private メソッドは持ってよい。
- 引数・戻り値・型ヒントは**インターフェース型**で書く。具象型を型ヒントに直書きしない。
- 外部からアクセスさせたい属性は、属性を公開するのではなく**アクセサメソッドをインターフェースに足す**。

```python
from abc import ABC, abstractmethod


class IModelEvaluator(ABC):
    """モデル評価処理の契約。"""

    @abstractmethod
    def evaluate(self, model: IModel, input_data: InputDto) -> OutputDto:
        ...


class RegressionModelEvaluator(IModelEvaluator):
    def evaluate(self, model: IModel, input_data: InputDto) -> OutputDto:
        # 回帰モデル固有の評価。利用側はこの型名を知らない。
        ...
```

利用側はこう書く。「どの評価器か」を意識しないので、新しいモデルを足しても呼び出し側は無改修。

```python
def run(evaluator: IModelEvaluator, model: IModel, input_data: InputDto) -> OutputDto:
    return evaluator.evaluate(model, input_data)
```

### 抽象化しない例外

過度な抽象化は害になる。次の型はインターフェース化しない。

- 標準ライブラリ・組み込み型（`datetime` / `str` / `dict` / `int` / `float` …）
- 値の集合が固定で実装差し替えの余地がない `Enum`
- 依存として安定している外部ライブラリの型（`numpy.ndarray` など）
- 値の保持だけを担う**データクラス（DTO）**

## 2. 依存性逆転（DIP）でレイヤーを守る

上位レイヤーは下位レイヤーの**抽象**に依存し、具象には依存しない。
これにより「上位 → 下位」の一方向依存（[3_layering_and_imports.md](./3_layering_and_imports.md)）を
個別の参照ではなく**設計**として固定できる。

- 実装の選択（どの具象を使うか）は利用側に漏らさず、生成箇所（次節のファクトリー）へ閉じ込める。
- リスコフ置換を守る: サブクラスは基底より**強い事前条件**・**弱い事後条件**を持たない
  （受け取る入力をより厳しくしない／返す保証をより弱くしない）。

## 3. 生成はファクトリーに集約する（Factory / Strategy）

インスタンスをクラスから直接 `__init__` で作らない。**ファクトリーメソッド／ファクトリークラス**を経由する。
これにより「設定値・分岐キーから、どの実装を返すか」という判断を一点に集約でき、
分岐が増えても利用側は変わらない（Open–Closed）。

```python
class ModelEvaluatorFactory:
    @staticmethod
    def create(model_type: ModelType) -> IModelEvaluator:
        # 「どの実装を返すか」をここだけが知る。戻り値は必ず抽象型。
        if model_type is ModelType.REGRESSION:
            return RegressionModelEvaluator()
        ...
```

設計上の取り決め:

- **戻り値の型は必ずインターフェース**にする（具象型を返さない）。
- ファクトリーの責務は「**どの実装かを判定して生成して返す**」まで。生成後の追加初期化は呼び出し側の責務。
  例外的に生成時初期化が必要なら、その意図を docstring に明記する。
- 分岐キーの渡し方は結合度が低い順に選ぶ:
  1. 単一の `Enum` / フラグ / 型で表せる → それを引数にする（シグネチャで分岐軸が分かる）。
  2. 複数フィールドの組合せが要る → 必要範囲に絞った部分 DTO を渡し、内部で分岐を導出する
     （どの属性で実装を選ぶかを docstring に明記し、分岐の組合せをテストする）。
- ステージや入力設定ごとにアルゴリズムを動的選択する場合は、
  **Strategy + Factory** を主要パターンとして使う。

> 例（このプロジェクトでの適用）
>
> 本リポジトリでは、回路モデルや計算アルゴリズムの選択を設定から切り替えるために、
> Strategy + Factory を使う。

## 4. 継承より委譲（実装継承の禁止）

実装の共通化を**実装継承**で行わない。共通処理は別クラスへ切り出し、**委譲**で使う。
（インターフェースの継承＝型の宣言は当然行う。禁止するのは「実装を再利用するための継承」。）

- 親クラスの実装に縛られた密結合を避け、組み合わせで機能を構成する。
- 共通ロジックは「持つ（has-a）」関係で注入し、「である（is-a）」関係に押し込めない。

## 5. 契約をコードと型とテストで表現する

インターフェースは利用側との**契約**。次の形で表現する。

- 事前条件: 引数の型（型ヒント）／満たすべき条件と違反時に送出する例外（docstring の `Raises`）。
- 事後条件: 戻り値の型（型ヒント）／戻り値・実行後の状態が満たすべき条件（**テスト**）。

事後条件の検証はテストに委ねる。詳細は [5_testing.md](./5_testing.md)。

## 横断クラスの慣行

設定・ロガーのような横断関心事は、当該クラスで未使用でも `__init__` で受け取り
`self._config` / `self._logger` として保持する（利用箇所が後から増えても口を変えずに済む）。
`__init__` は値・オブジェクトの保持だけにとどめ、重い処理を書かない。

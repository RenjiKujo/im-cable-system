# テスト方針（層 3: 横断概念）

テストは「契約（[2_design_principles.md](./2_design_principles.md) の事後条件）を固定する手段」と位置づける。
インターフェースが保証する戻り値・状態を、利用側の視点でテストに書き下す。

## 基本方針

- **実装にはテストを伴う。** 戻り値・実行後の状態が満たすべき条件はテストで表現する。
- テストは**公開窓口**（[3_layering_and_imports.md](./3_layering_and_imports.md)）から import し、
  実利用と同じ経路で検証する（リファクタリング耐性のため）。
  - 例外: 窓口に載せていない内部実装のユニットテストに限り、リーフ直 import を許容する。
    その場合テスト先頭の docstring に「内部実装の単体テスト」である旨を 1 行書く。
  - テストのためだけに内部実装を公開窓口の `__all__` へ載せない（公開 API に内部詳細を漏らさない）。
- ファクトリーは**分岐ごと**（返る実装型・`Enum` の値ごと）に、正しい実装が返ることをテストする。

## ディレクトリ構成

テストツリーは、本番コードの責務やパッケージ構成と対応づける。
どの深さまで接頭辞を付けるか、どこから本番側と同名にするかはプロジェクトごとに定義する。

- テストの探索範囲・クラス名／メソッド名の命名規約・マーカーは `pyproject.toml` の
  `[tool.pytest.ini_options]` が正本（[README.md](./README.md) の正本マップ参照）。

> 例（このプロジェクトでの適用）
>
> `tests/` 直下を深さ 0 と数え、深さ 1・2 のディレクトリ名は `test_` で始める
> （例: `tests/test_algorithm/test_execute_algorithm/`）。深さ 3 以降は本番側と同名にし、
> `test_` 接頭辞は付けない（例: `.../simulate/`）。
> `conftest.py` だけの階層や、テスト間で共有する静的資産ディレクトリ（`data/` 等）は
> `test_` 接頭辞を必須としない。
> 例外: `tests/test_docs/` は単一パッケージに対応しない
> （`docs/` とコード・設定の横断的な整合性を検証するテストのため）。

## 実行

- プロジェクトで定義した仮想環境・依存関係を使い、システムの `python` 単体での実行は避ける。
- 重いテストは専用マーカーを付け、通常確認・CI では必要に応じて除外する。

```bash
# 例: 通常確認
python -m pytest -q
```

コード変更後はテストを実行し、pass するまで修正する。

> 例（このプロジェクトでの適用）
>
> リポジトリルートの `.venv` を使う。通常確認では `slow` を除外し、必要に応じて全テストを実行する。
>
> ```bash
> .venv/bin/python -m pytest -m "not slow" -q
> .venv/bin/python -m pytest -q
> ```

## ログ計測

主要なオーケストレーション・重い計算処理には、開始・終了と処理時間を記録する。
一方、細かい下位メソッドまで一律に計測するとログがノイズ化するため、計測対象を絞る。

> 例（このプロジェクトでの適用）
>
> 主要なオーケストレーション・重い計算処理には `@timer` を付ける。
> ノイズ抑制のため一定時間未満のログは抑制する（入口・出口トレースが必須な最上位メソッドを除く）。
> 計算器・変換器などの下位メソッドには原則付けない。

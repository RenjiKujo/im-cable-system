# レイヤー構成と import 規約（層 3: 横断概念）

依存方向を構造で固定し、変更の波及を局所化するための取り決め。
「どのレイヤーが何に依存してよいか」と「どこから import してよいか」を分けて定義する。

## レイヤーと依存方向

コードを責務ごとの層に分け、依存は**上位から下位への一方向のみ**許す。
具体的な層の名前・数・責務はプロジェクトごとに定義する。
その際、**何をもって「上位」とするかの軸を 1 つ決めて明示する**
（呼び出し順＝オーケストレーションの深さ／抽象度／安定度などのうち一つ）。
軸を決めずに層だけ並べると、層を増やすときや「この責務はどの層か」を判断するときに
拠り所が無くなる。

- **下位から上位への import は禁止。**
- 依存先は**具象ではなく抽象（インターフェース）** にする
  （[2_design_principles.md](./2_design_principles.md) の「抽象への依存」）。
- レイヤー間のデータ受け渡しは DTO や値オブジェクトを契約として用いる。
  DTO を層ごとに定義するか、全層から参照できる最下層へ集約するかはプロジェクトごとに決める
  （層をまたぐ DTO を層ごとに定義すると層間の変換コードが増えるため、集約を選ぶ場合が多い）。

> 例（このプロジェクトでの適用）
>
> engine（`src/im_cable_system/engine/`）は
> `pipeline → processor → algorithm → domain → shared` の 5 層で構成する。
> 上位／下位の軸は**呼び出し順（オーケストレーションの深さ）**であり、抽象度や安定度ではない
> （そのため domain は最下層ではなく shared の一つ上に位置する）。
> DTO は層ごとに定義せず、最下層の `src/im_cable_system/engine/shared/dto` に集約して
> 全層で共有する。
> `runner/`・`apps/`・`scripts/` は engine の外側のクライアントでこの 5 層には
> 属さない（それぞれ独自の内部構造を持ちうるが、engine へは公開窓口経由でのみ
> 依存する）。層の正本はそれぞれ
> [`../architecture/0_component.md`](../architecture/0_component.md) と
> [`../apps/web/0_overview.md`](../apps/web/0_overview.md)。

## 公開窓口（ファサード）経由の import

レイヤーやコンポーネントの**境界をまたぐ**参照は、各パッケージの**公開窓口**
（再エクスポートを明示した `__init__.py`）からのみ import する。
実装ファイル（リーフモジュール）への直 import は、境界をまたぐ場合は禁止する。

**例外**: パッケージルートに公開窓口を置かず、**単一のリーフ契約（IF モジュール）だけ**を
置く構成では、そのモジュールを層外から直 import してよい。窓口はサブパッケージ側に
置き、ルートは契約 1 本のみを提供する。この構成を採るモジュールは、その理由と
import の書き方を自身の docstring に書く。

| 呼び出し元 → 呼び出し先 | import の仕方 |
|---|---|
| 別レイヤー／別の責務ツリー | 公開窓口の `__init__.py` 経由（**必須**） |
| 同一レイヤー・同一責務ツリー内 | リーフモジュールへの直 import を**許容**（循環依存は禁止） |

判断の軸は「同じレイヤー／同じディレクトリか」ではなく、**同一責務ツリーか**。
同じレイヤーでも責務が違うサブツリーをまたぐとき（例: 入力変換系 ↔ モデル評価系）は
窓口経由を優先する。

### 公開窓口の作り方

- 実装モジュールを置くディレクトリには原則 `__init__.py` を置き、その docstring に**ディレクトリの責務**を書く。
- 境界外へ公開するシンボルは、窓口 `__init__.py` で再エクスポートし `__all__` に列挙する。
- `__all__` を持たない `__init__.py` は「公開窓口ではない（案内・束ね役）」とみなす。
- 窓口に載せない（＝層外非公開の）シンボルは、実装モジュールの docstring に**非公開の理由**を書く。

### 公開窓口の深さ

レイヤーのルートそのものを常に公開窓口にするのではなく、責務単位・機能単位の
サブパッケージを公開窓口にする。どの深さを窓口にするかは、公開 API として安定させたい
粒度に合わせて決める。これにより、内部のリファクタリングを公開 API に漏らさずに行える。

> 例
>
> `domain` は中分類／責務単位、`processor` はステージ単位、`pipeline` は機能パッケージ単位を
> 公開窓口にする。

## 新規シンボル追加時のチェックリスト

1. 属するレイヤーを決め、依存が**上位 → 下位**のみか確認する。
2. 境界外から使うなら、公開窓口へ再エクスポートし `__all__` に追加する。
3. 呼び出し側は公開窓口から import する（境界をまたぐリーフ直 import は禁止）。
4. 公開しないなら、実装モジュールの docstring に非公開理由を書く。

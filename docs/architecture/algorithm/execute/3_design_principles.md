# Executeアルゴリズム設計前提

## 概要

この文書は、Execute アルゴリズムで守る設計前提と判断理由を記載する。コードから追えるクラス構造ではなく、計算の基準、責務境界、拡張時に崩してはいけない契約を中心に扱う。

パラメータ推定の残差設計は [`curve_fitting_consistency.md`](../../../model/curve_fitting_consistency.md) を参照。

## 責務境界

Processor 層は `InputDtos` の分配・並列化・集約を担当し、Algorithm 層は単一 `InputDto` の計算を担当する。これにより、上位層は「何件をどう回すか」に集中し、下位層は「1 件をどう正しく計算するか」に集中できる。

forward の計算順序は `build_model -> simulate -> validate_itm_dto` に固定する。検証を任意の呼び出し側に任せると漏れや順序違いが起きやすいため、Algorithm 層のオーケストレーターが最後まで責任を持つ。

## Direct / Iteration の分岐

電流依存イミタンスを含まないモデルでは、入力条件だけで等価回路が決まるため Direct 実装で十分である。一方、IM やケーブルに電流依存モデルが含まれる場合、等価回路のパラメータは計算結果の電流に依存する。

そのため Iteration 実装では、前回のシミュレーションで得た電流を次回のモデル構築へ渡し、線電流の変化が閾値未満になるまで反復する。分岐条件は Factory に集約し、Processor 層や Pipeline 層に電流依存モデルの知識を漏らさない。

## 物理量の基準

イミタンス、電圧、電流、電力は、内部計算ではスター等価の 1 相量を基準にする。線間電圧から相電圧への変換や、3 相合計電力への変換は計算器側で一貫して扱う。

電力 DTO は 3 相合計の複素電力を保持する。相量ベースの計算結果を 3 相合計へ変換して保持することで、入力電力、損失、効率の比較基準を揃える。

ケーブルが存在しない場合は、完全導体・完全絶縁の擬似ケーブルモデルとして扱う。`None` を計算途中で特別扱いし続けるより、回路モデルとして表現した方が、システムモデル構築とシミュレーションの責務を単純に保てる。

### 軸（Shaft）出力（軸出力控除を含む場合）

IM の軸出力（`ItmImPowerDto.output_power`）は、両軸（`im_friction_windage` / `im_stray_load`）が `NONE`（必須軸だが、ゼロ損失の明示的なモデル種別）のときは二次負荷支路電力の総和と一致する。摩擦・風損・漂遊負荷損を有効にした場合は、`output_power = Σ secondary_load_power − P_FW − P_stray`（実部のみ減算）として、軸出力控除を差し引いたものを軸出力とする。両損失を `total_loss_power` にも含めるため、`validate_energy_conservation`（複素のまま比較）は構造的に破れない。

「軸出力控除」は摩擦・風損と漂遊負荷損を**役割**（二次負荷支路電力から引いて軸出力を得る）で括った呼び名であり、損失分類の総称ではない。規格（IEC 60034-2-1 / IEEE 112）の損失分類では機械損は摩擦・風損のみを指し、漂遊負荷損は追加負荷損として別枠に置かれる。摩擦・風損は引き続き機械損と呼んでよいが、漂遊負荷損を機械損と呼ばない。

摩擦・風損と漂遊負荷損は、イミタンス（インピーダンス・アドミタンス）を持たないサブシステムである。他の IM 部分（一次・励磁・二次）は「1 相で計算して 3 相へ変換」する経路（`build_model/` → `simulate/`）を通るが、この 2 つは `ImSeriesDto.nameplate_power`（銘板電力、定義上すでに 3 相合計）を基準に電力計算段（`simulate/power/calculate_im_shaft_output_deduction/`）で直接計算し、二次負荷電力から減算する。「1 相 → 3 相変換」を経ない唯一の量である。数式・記号の正本は [`im_friction_windage.md`](../../../model/equations/im_friction_windage.md) / [`im_stray_load.md`](../../../model/equations/im_stray_load.md)。

## 配列レイアウト

forward の必須軸は `slip`, `frequency`, `input_line_voltage` である。これらは回路計算を定める外生変数であり、`InputDto` の時点で存在している必要がある。

参照軸は、配列 shape を決める軸として扱う。電流は回路から求まる結果なので、通常の forward 入力では参照軸にしない。電流依存モデルの反復では、前回結果の電流を array layout に合流させて次回のモデル構築へ渡す。

Itm から ArrayLayout へ戻す変換は、現時点ではイテレーション用途に限定される。利用箇所が増えた場合は、軸名やキー名の契約を Shared 層へ寄せ、変換処理を Domain 層へ切り出すことを検討する。

## Calculator / Builder の分離

モデルタイプごとの分岐は Factory に置き、実際の計算差分は Builder / Calculator の実装へ閉じ込める。これにより、新しい IM モデルやケーブルモデルを追加しても、Processor 層や forward オーケストレーターの責務を増やさずに済む。

ただし、モデルタイプの粒度を細かくしすぎると Factory の分岐が複雑になる。同一モデルタイプ内の小さな計算差分は、必要に応じて実装内部の戦略や private 処理として扱う。

## 検証の位置付け

`validate_itm_dto` は、数値計算そのものではなく、計算結果が物理制約や設定上の許容範囲を満たすかを確認する後段処理である。重大度や有効化フラグは設定で切り替えられるようにし、検証ルールの追加は Validator の追加で吸収する。

検証を Algorithm 層の最後に置くことで、下位の Calculator は個別の計算責務に集中でき、上位層は「検証済みの ItmDto を受け取る」という契約で扱える。

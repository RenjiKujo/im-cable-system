# Executeアルゴリズムテスト方針

## 概要

Execute アルゴリズムのテストでは、単一 `InputDto` に対する計算契約を保証する。個々のテストケースやデータセットの詳細はテストコードを正とし、この文書ではテストの粒度と責務分担を示す。

## テストの粒度

Execute のテストは、次の粒度に分ける。

- **Factory テスト**: 入力モデルに応じて Direct / Iteration のどちらが選ばれるかを検証する。
- **Orchestrator テスト**: `build_model -> simulate -> validate_itm_dto` の順序で単一 `InputDto` が `ItmDto` へ変換されることを検証する。
- **Builder / Calculator テスト**: モデルタイプごとの DTO 構築や数値計算の契約を検証する。
- **Validation テスト**: 有効化された検証ルールが期待どおりに成功・失敗を返すことを検証する。
- **EstimateParams テスト**: 残差ベクトル、重み、推定対象パラメータの適用が設計どおりであることを検証する。

Processor 層の逐次・並列処理や `InputDtos` の集約は、Processor 層のテストで扱う。Execute 層では 1 DTO 単位の正しさに集中する。

## Direct / Iteration

Direct 実装では、電流依存モデルを含まない代表ケースで、1 回のモデル構築とシミュレーションで `ItmDto` が生成されることを確認する。

Iteration 実装では、電流依存モデルを含む代表ケースで、反復が収束し、収束後の `ItmDto` が検証まで到達することを確認する。反復回数や途中値の詳細よりも、入力電流を次回モデル構築へ渡す契約と、収束条件を満たす契約を重視する。

Factory テストは分岐の網羅に限定する。Factory 経由で execute まで通る smoke は残すが、Direct / Iteration の詳細挙動は各実装の単体テストで検証する。

## 数値計算のテスト方針

数値計算は、完全一致ではなく、物理式・単位・配列 shape・許容誤差を明示して検証する。特に次の観点を重視する。

- スター等価 1 相量と 3 相合計電力の変換が一貫していること。
- `slip`, `frequency`, `input_line_voltage` の参照軸 shape と出力 DTO の shape が一致すること。
- NaN は評価対象外の表現として扱い、inf は検出時に失敗させること。
- 数値ガードの境界値（`<= eps`, `>= max_mag`）が共通ルールどおりに扱われること。

## テストデータ

テストデータは、IM モデルタイプ、ケーブル構成、配列レイアウトの代表組み合わせを持つ。全組み合わせを使うテストは回帰検出には有効だが、失敗時の原因が見えにくくなるため、単体テストでは代表ケースを明示し、広い組み合わせは smoke / 統合寄りのテストに寄せる。

ArrayLayout の電流キーなど、Itm から次回入力へ戻す契約は、実装のゲッターとテストデータのキーを一致させる。契約が広がった場合は、リテラル重複を避けるため共通定数化を検討する。

## EstimateParams

パラメータ推定のテストでは、最適化アルゴリズムの収束そのものよりも、残差設計の契約を優先して検証する。

- カタログ値とシミュレーション値が同じ参照面・同じ軸で比較されること。
- 残差重みがチャネルごとに適用されること。
- 推定対象パラメータの descriptor が DTO の正しい位置へ適用されること。
- カタログ 4 量の自己無矛盾性に依存しすぎない設計になっていること。

カタログ性能カーブとの構造的な不整合は [`estimate_params_curve_fitting_consistency.md`](./estimate_params_curve_fitting_consistency.md) を参照。

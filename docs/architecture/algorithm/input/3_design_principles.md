# Inputアルゴリズム設計前提

## 概要

この文書は、Input アルゴリズムで守る設計前提と判断理由を記載する。コードから追えるクラス構造ではなく、各段の責務分担、検証の置き場所、拡張時に崩してはいけない契約を中心に扱う。

## 4 段の責務分担

`build_input_dto` は 4 段を固定順で呼び出す。各段は「どこで失敗を判定するか」を明確に分ける。

- `validate_job_spec`: ファイルを開く前に確認できる軽量チェックに限定する。パス存在や必須フィールドの非空など。
- `load_data`: `LoadedData` を作れない場合のみ raise する。ファイル読み取り不可、ヘッダ欠落、数値変換失敗、カタログキー未登録など、ファイル構造の破綻が対象。
- `assemble_input_dto`: `InputDto` を作れない場合のみ raise する。フィールド単体の値域・有限性・単位は各 DTO の `__post_init__` が担う。
- `validate_input_dto`: フィールド単体を超える整合を意図的に重く検証する。

この分担により、上流の段は「構築できるか」だけに集中でき、値レベル・関係式レベルの整合は下流に集約される。

## 検証を最後に重く置く

DTO 構造の整合、SI 基本単位の整合、DTO 横断の整合（参照軸長さ、カタログと候補のシリーズ名整合など）、物理関係式（T·ω と P など）、定格と供給電圧の乖離 warning は、すべて最終段の `validate_input_dto` に置く。

検証を上流に散らすと、ロードや組み立ての途中で部分的な検証が走り、責務が濁る。重い検証を最後にまとめることで、各段の契約を単純に保てる。

## モード差の吸収

forward の CartesianGrid / OperatingPoints は、参照軸の選び方だけが異なる。そのためオーケストレーターにモード分岐を持たせず、`reference_axes` を生成時に Assembler へ注入する形で差を吸収する。

estimate_params は「1 TSV → 複数 InputDto」を扱う。候補直積の展開は TSV のパース結果に依存するため Loader に閉じ込める。組み立て・検証の複数件ループはオーケストレーターが持ち、Assembler / Validator は単一件処理の契約に保つ。

この切り分けにより、forward と estimate_params で Assembler / Validator の粒度を揃えられる。

## 公開境界

層外（Processor / Pipeline）へ公開するのは、実行モードに対応するモード別オーケストレーターインターフェースだけにする。共通インターフェースは派生で `create` 引数が変わり、そのまま層外へ出すとリスコフ置換に反するため公開しない。

`LoadedData` などの中間表現も Input 内部に閉じ込め、層外には検証済みの `InputDto` / `InputDtos` だけを渡す。

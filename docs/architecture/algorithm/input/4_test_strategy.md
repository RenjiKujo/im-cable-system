# Inputアルゴリズムテスト方針

## 概要

Input アルゴリズムのテストでは、ジョブ仕様から検証済み `InputDto` / `InputDtos` が構築される契約を保証する。個々の入力ファイルやテストケースの詳細はテストコードを正とし、この文書ではテストの粒度と責務分担を示す。

## テストの粒度

Input のテストは、4 段に対応する粒度に分ける。

- **JobSpecValidator テスト**: パス欠如や必須フィールド欠落が、ロード前に期待どおり失敗すること。
- **Loader テスト**: ファイル構造の破綻（ヘッダ欠落、数値変換失敗、カタログキー未登録など）でのみ失敗し、`LoadedData` を構築できること。
- **Assembler テスト**: `LoadedData` から `InputDto` が組み立てられること。フィールド単体の契約違反と、1 つの DTO 内で閉じたキー集合の過不足（モデル係数名など）は DTO の `__post_init__` 側で検出されること。Loader 側がそれを先回りして弾いていないこと。
- **InputDtoValidator テスト**: 構造整合・単位整合・DTO 横断整合・物理関係式の検証が、期待どおり成功・失敗を返すこと。
- **Orchestrator テスト**: `build_input_dto` が 4 段を固定順で実行し、検証済みの `InputDto` / `InputDtos` を返すこと。

## モード別の観点

forward では、CartesianGrid / OperatingPoints の参照軸の違いが `reference_axes` 経由で反映され、いずれも単一 `InputDto` を構築できることを確認する。

estimate_params では、統合 TSV から候補直積が展開され、各候補に対応する `InputDto` が `InputDtos` にまとまることを確認する。展開件数と組み立て・検証の対応関係を重視する。

## 失敗系の方針

各段が「自分の責務範囲でのみ失敗する」ことを重視する。

- ロード前に検出すべき不備が、`_load_data` まで進まずに失敗すること。
- ファイル構造の破綻が `_load_data` で、フィールド契約違反が DTO 構築で、横断整合違反が `_validate_input_dto` で検出されること。
- 定格と供給電圧の乖離など warning 扱いの項目が、エラーではなく warning として扱われること。

これにより、失敗時にどの段の問題かを切り分けやすくする。
